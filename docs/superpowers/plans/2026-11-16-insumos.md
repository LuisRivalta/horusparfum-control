# Insumos (Parte 1 do módulo Anúncios) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Controle de insumos com estoque e custo médio, listas de insumos por tipo de item e por envio, baixa automática nas vendas e decants, decant de 2,5 ml e decant tirado de mais de um frasco.

**Architecture:** Schema e regras atômicas em PL/pgSQL (padrão do projeto: RPC = fonte da verdade gravada), prévia ao vivo em libs TypeScript puras com `decimal.js` (TDD com Vitest), telas React no módulo Estoque. As RPCs de venda/decant ganham parâmetros novos **com default**, para o frontend antigo continuar funcionando entre a aplicação do SQL e o deploy do frontend.

**Tech Stack:** React 19 + Vite + TS + Tailwind 4, TanStack Query, Supabase JS, decimal.js, Vitest + Testing Library; PostgreSQL/Supabase (PL/pgSQL).

**Spec:** `docs/superpowers/specs/2026-11-16-anuncios-design.md` — seção 5 (Parte 1). Ler a seção 5 inteira antes de começar.

## Global Constraints

- SQL do Horus é aplicado **à mão pelo Luis** no SQL Editor do projeto `wyobbztexoofhqdttxzq`. **Nunca** usar o MCP do Supabase desta máquina (aponta para outro projeto). O executor escreve o `.sql`, valida a sintaxe localmente e pede ao Luis para aplicar.
- Nada vem pronto: **nenhum insumo é semeado**. Só os "contêineres" de lista são criados (decant 2,5 / 5 / 10 ml, frasco, envio_decant, envio_frasco), vazios.
- Tamanhos de decant: **2,5 ml, 5 ml, 10 ml**. Colunas de ml passam a `numeric(6,1)`.
- Custo unitário de insumo com 4 casas (`numeric(12,4)`); valores de venda/custo gravados continuam com 2 casas.
- Compra de insumo lança despesa em `transacoes`: `tipo='saida'`, `categoria='Insumos'`, `origem='insumo'`.
- Estoque de insumo **pode ficar negativo**: falta de insumo no sistema nunca bloqueia venda (o estoque se acerta na recompra).
- Dinheiro sempre com `formatBRL()` de `src/lib/utils.ts`; imports com `@/`; componentes em PascalCase.
- Toda função PL/pgSQL nova ou reescrita: `language plpgsql`, `set search_path = public`, mensagens de erro em português.
- Mudança de tipo de parâmetro (`int` → `numeric`) cria sobrecarga no Postgres: **`drop function` da assinatura antiga antes do `create`**.
- Regra de auditoria da máquina: todo `.py/.js/.ps1` criado/modificado é registrado com `Registrar-Auditoria__Claude_Code_MS125_luisgfr.ps1` (ver CLAUDE.md global). `.ts/.tsx/.sql` não estão na lista.
- Commit só quando o Luis pedir (CLAUDE.md). Os passos "Commit" abaixo ficam prontos, mas só rodam com o ok dele.

## Review Focus

1. **Venda de decant cujo frasco aberto não basta e não há lacrado** — a RPC tem que recusar com mensagem clara ("ml insuficiente: X disponíveis") e a tela tem que oferecer completar com outro perfume, nunca gravar ml negativo. Teste em Task 2 (`planejarOrigens` → `null`) e no script de verificação da Task 4.
2. **Cancelar/excluir venda que abriu frasco lacrado na confirmação** — o estorno devolve os ml a cada origem; o frasco que ficou `esgotado` volta a `ativo` só se não existir outro ativo do mesmo perfume; se existir, os ml voltam para o ativo e o lacrado aberto **não** volta ao estoque (já foi aberto). Teste na verificação da Task 4.
3. **Editar venda** (`editar_venda` estorna e regrava) não pode duplicar consumo de insumo nem perder origens. Teste na verificação da Task 4.
4. **Compra com saldo contado maior que o do sistema** — vira `acerto` positivo, não "perda negativa"; custo médio usa o saldo contado. Teste em Task 1.
5. **Insumo apagado/inativado que ainda está numa lista** — lista some com ele na tela da venda sem quebrar; `insumos` usa `ativo=false` em vez de delete quando houver movimentação (FK `restrict`). Teste na Task 5.

### Task 4: Migração das RPCs — baixa de insumos e decant com várias origens

**Files:**
- Create: `supabase/migrations/20261116110000_insumos_rpcs.sql`
- Create: `supabase/checks/20261116110000_insumos_rpcs_check.sql`
- Base (copiar a versão mais recente de cada função e alterar): `registrar_venda`, `editar_venda` → `20260806_custo_unitario_opcional_venda_itens.sql`; `cancelar_venda` → `20260622142718_fix_cancelar_venda_decant_fk.sql`; `excluir_venda` → `20260729_excluir_venda.sql`; `registrar_consumo_decant`, `corrigir_consumo_decant` → `20260713_correcao_unificada_transacoes.sql`; `cancelar_consumo_decant` → `20260720160000_cancelar_consumo_decant.sql`.

**Interfaces:**
- Consumes: schema da Task 3; formato `origemParaJson` da Task 2; `ItemInsumo` da Task 1 (no JSON: `{insumo_id, quantidade}`).
- Produces:
  - helpers internos (sem grant ao front):
    `_baixar_insumos(p_itens jsonb, p_venda_id uuid, p_decant_id uuid, p_responsavel text) returns numeric` — para cada `{insumo_id, quantidade}` grava mov `consumo` (quantidade negativa, `custo_unitario` = `custo_medio` atual), subtrai do estoque, devolve o custo total (2 casas). Insumo inexistente → exceção.
    `_estornar_insumos(p_venda_id uuid, p_decant_id uuid) returns void` — para cada `consumo` ainda não estornado daquela venda/decant grava `estorno` (+quantidade) e devolve ao estoque.
    `_consumir_origens(p_origens jsonb, p_decant_id uuid) returns numeric` — percorre as origens em ordem; `frasco_id`: trava, exige `status='ativo'` e `ml_restante >= ml`, subtrai, marca `esgotado` se zerar; `abrir_produto_id`: trava o produto, exige `estoque_atual >= 1`, exige que **não haja frasco ativo** daquele produto (o aberto anterior tem que ter sido esgotado por uma origem anterior da mesma lista), tira 1 do estoque + grava `movimentacoes` (saída, motivo `'Abertura de frasco para decant'`), cria `frascos_abertos` com `ml_total = volume_ml`, subtrai o ml, grava `decant_origens.abriu_frasco = true`. Custo de cada origem = `round(ml * custo_medio / ml_total, 2)`. Devolve o custo total.
    `_devolver_origens(p_decant_id uuid) returns void` — devolve os ml de cada `decant_origens`: se o frasco de origem está `ativo`, soma nele; se está `esgotado` e não há outro ativo do produto, reativa e soma; se está esgotado e há outro ativo, soma no ativo (limitado a `ml_total` do ativo; excedente é descartado). Nunca devolve frasco lacrado ao estoque.
  - `registrar_venda(... mesmos parâmetros ..., p_titulo text default null, p_insumos_envio jsonb default '[]')`:
    item `decant` aceita `origens: [...]` (se ausente, usa `frasco_id` + `ml*quantidade` como origem única — compatível com o frontend atual) e `insumos: [...]` (se ausente, nenhum insumo — compatível); `custo_unitario` do decant = custo das origens ÷ quantidade; `custo_embalagem` = custo dos insumos do item ÷ quantidade (se `insumos` ausente, mantém o `custo_embalagem` enviado). Item `produto` também aceita `insumos`. `p_insumos_envio` é baixado com `p_venda_id` e o custo vai para `vendas.custo_envio`, que entra em `lucro_bruto` (`total_bruto − taxa − frete − total_custo − custo_envio`). `decants.frasco_id` = frasco da primeira origem.
  - `editar_venda(..., p_insumos_envio jsonb default '[]')`: mesma regra; estorna (origens + insumos) antes de regravar.
  - `cancelar_venda(p_venda_id)` e `excluir_venda(p_venda_id)`: chamam `_devolver_origens` para cada decant da venda e `_estornar_insumos(p_venda_id, null)` + `_estornar_insumos(null, decant_id)`.
  - `registrar_consumo_decant(p_frasco_id uuid, p_ml numeric, p_classificacao text, p_custo_embalagem numeric, p_responsavel text, p_origens jsonb default null, p_insumos jsonb default '[]')`: com `p_origens` usa as origens; sem, usa `p_frasco_id`/`p_ml`. `perda` não baixa insumos (ignora `p_insumos`). Custo de embalagem gravado = custo de `p_insumos` quando informado, senão `p_custo_embalagem`.
  - `corrigir_consumo_decant(... p_ml numeric ...)` e `cancelar_consumo_decant(p_decant_id)`: devolvem origens e insumos.
  - **Antes de cada `create`**, `drop function if exists` da assinatura antiga com `int` / sem os parâmetros novos.
